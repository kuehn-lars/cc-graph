# F09 Terminal graph and layout

| Status | Milestone | Owner | Checked against | Depends on |
| --- | --- | --- | --- | --- |
| Verified | v0.2 | Lars Kühn (@kuehn-lars) | Claude Code 2.1.296 | F04, F06, F08 |

## Problem

A list says what Claude saw but not how it hangs together: which files depend on a change, where the ghosts sit, what Claude is touching right now. In a terminal there is no canvas to draw that on, and a graph of one-cell glyphs joined by block staircases, scattered at random, says nothing at all: nodes are dots, edges merge into blobs, and most files have no name on screen.

## Solution

In the terminal the pane draws the graph the way Claude Code draws itself: rounded boxes on the terminal's own background, in Claude Code's own colours. Each file is a box that holds its list glyph, its name and its change word; a solid border means in context, a dashed one not, and a bar along the bottom says what it costs. Import edges are box-drawing lines at right angles, and importers sit above what they import, so the graph reads top down like a diagram. The file Claude just touched has a border in Claude's orange, its edges light up in the same colour, the border flashes once, and a line under the graph says what it is. A header meters the context, and a legend names only what is on screen.

## User stories

1. As a terminal user, I want a real graph drawn in the pane, so that I see the shape of what Claude touched without leaving the terminal.
2. As a developer, I want every file named on the graph, so that I never have to guess what a box is.
3. As a developer, I want to see what is in context at a glance, so that solid and dashed boxes tell me what Claude knows without reading.
4. As a developer, I want importers above what they import, so that dependencies read top down like a diagram.
5. As a developer, I want the file Claude just touched to stand out, with its edges, so that I can follow what is happening while the turn runs.
6. As a developer, I want the size of a change next to the file, so that I see how much Claude edited without opening the list.
7. As a developer, I want a file's size drawn on its box, so that I see where the context goes.
8. As a developer, I want each file to keep its place as the graph grows, so that I can follow it across turns.
9. As a developer, I want the graph to use the whole pane, so that a small graph is not a cluster in a corner.
16. As a Claude Code user, I want the graph to look like part of Claude Code, so that it reads as one product and not a foreign widget.
10. As a developer, I want a header that meters the context in words and a bar, so that I know how full the window is.
11. As a developer, I want a legend for what is on screen only, so that I never have to remember the encoding.
12. As a developer, I want memory files named under the graph, so that I see what instructions are loaded.
13. As a developer with a narrow pane, I want the graph to scale down and fall back to the list, so that it never draws garbage.
14. As a colour-blind developer, I want every state and change told by a shape or a word as well as a colour, so that nothing depends on colour alone.
15. As a developer, I want the same facts in the list, so that choosing the list never costs me information.

## Implementation decisions

- **Boxes, not braille.** A braille shape is built from dots on a font's grid, so two discs of one radius look different where they fall on cells differently, and the gaps between dots read as grain. A box is made of whole characters and looks the same wherever it lands. It holds the list's own glyph and the name, so the graph and the list speak one language, and the size moves into a bar on the box's bottom side. State is told by the glyph and by the border, solid or dashed, as well as by colour (NFR-A1).
- **Native look.** Rounded boxes on the terminal's background, `✻` and `⏺`, and the theme's colours are how Claude Code draws its own prompt, dialogs and tool calls. Claude's orange marks one thing only, what Claude is working on now: the focus's border, its edges, the `⏺` of the now line. Everything else stays in Claude Code's greys.
- **Theme keys where the API allows.** `Text` takes a theme key and follows the person's theme. A `Raster` takes raw colours only, and NFR-S1 allows no `$.config.list` to read the theme, so the graph paints the dark theme's values and leaves names in the terminal's default foreground, which reads in every theme (F09-Q3).
- **Edges at right angles.** Box-drawing lines meet boxes cleanly and merge where they share a run, with a junction character instead of a blob. The turn goes where the line crosses the fewest boxes, the earliest such, so the edges of one node fan out from one point like a tree; a line may enter its target anywhere along the top to slip past a box above it, and crosses a frame at `┼`. Importers sit above what they import, so direction reads from position alone; arrowheads are not needed.
- **Folders as frames, in layers.** A folder is what a person navigates by, and two `index.ts` mean nothing without one. A titled frame around a folder's boxes says where each file lives without a word per box, the way an architecture diagram draws a package. The folders stack in layers, importers on top, so edges run down between rows like a bus and never back up; inside a folder the same rule orders the lines. Folders without imports, such as the root's `README.md` and `package.json`, fill free space at the side instead of taking a row. Positions from `layout` still order folders and nodes left to right, so a graph keeps its arrangement as it grows. When space runs out a folder's boxes become one-row tags before anything is left out.
- **One focus.** The selected node, or else the one Claude touched last, is the focus: Claude's colour on its border and edges, and the now line saying it in words. Everything else recedes, so the eye lands on what is happening.
- **New nodes settle freely.** The 2-unit cap of R4 is for nodes people have seen. A node arriving starts by its importer (or importee) and moves freely in its first pass; capping it too left every node where its folder's hash put it, which is why the first graph looked random.
- **A flash, not a ripple.** The touched box's border runs from white through Claude's shimmer colour to Claude's colour, as Claude Code's own spinner shimmers. It costs four blits and no render; the wiring keeps the last raster's size, and the pulse still waits for the queue so the layout write's redraw does not wipe it.
- **Memory as text.** Memory files have no edges and no position; a named line under the graph says more than a row of squares.
- **Layers.** `layout` is unchanged. `render` draws the boxes, edges, meter, now and legend lines; the wiring passes the focus (selected or now) and the pulse frames. Every `$` call stays in the wiring.
